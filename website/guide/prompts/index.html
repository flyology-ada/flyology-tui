Guide

Build a read-eval-print loop.

Start from a prompt that answers no keys. Finish with one that evaluates arithmetic across several lines, highlights the transcript below it, completes the word at the cursor, and keeps its history between runs. The last two steps put several of these prompts on screen at once, in windows or in panels.

Working baseline

Run the example.

The finished program is examples/src/repl.adb, and every extract below comes from it. Run it first, so you can compare each step against the finished program.

The loop evaluates integer arithmetic. A word that starts with a colon, such as :demo, is a directive rather than an expression.

  • Enter 1 + 2 for a result.
  • Enter :demo to load a three-line input.
  • Enter :new to open a second session.
  • Press F2 to move the sessions between the four placements of Step 07.

The example renames the packages it uses. Editors is Line_Editors, Marks is Highlights, Frames is Windows, and Panels is Panel_Groups. Menus is its instantiation of the generic Completions, and Histories keeps its own name. Scrollback is the example’s own transcript type, defined in Step 04.

The steps below build this program in order. The program uses the application loop from Application loop, so each extract belongs in Update or Present unless the text says otherwise.

Step 01

Define the session record.

One prompt needs more than an editor. It needs somewhere to put the candidates it offers, the lines it has already printed, and the frame it may later be drawn in. Collect that in one record, with a flag marking the session open, and the rest of the program has one thing to pass around.

The record deliberately holds no screen position. Step 07 depends on that, because it places this same record inline, docked, in a window, and in a panel.

Create has no default for the prompt markers, the word separators, or the duplicate policy. Each of those is application policy, so the caller must state it.

The six capacities are discriminants, so the bounds belong to the model type. The two buffer bounds and the four history bounds do not behave the same way when an operation exceeds them:

  • Max_Code_Points and Max_Lines bound the buffer. The model refuses the whole edit and leaves content, cursor, selection, and history unchanged.
  • Max_Undo_Entries, Max_Undo_Code_Points, Max_Recalled_Entries, and Max_Recalled_Code_Points bound the undo and command histories. The model evicts the oldest entry and applies the operation.

Note the separator set, which omits the colon. A directive such as :help is therefore a single word. Step 05 depends on that: Tab after :h completes the directive, not the letter.

Sessions also need distinct screen positions. Initialize replaces every frame with a staggered one, so a second window does not hide the first.

Run the example and this is all the record produces: >>> an expression, or :help, the marker followed by the placeholder from the last argument. No key changes it yet, because nothing has fed the record an event.

Step 02

Handle the submission action.

Nothing reaches the prompt yet. Feed it each terminal event, and Handle updates the editor and returns the one thing the editor cannot decide for itself: what the application should now do.

Submission is the clearest case. The editor never evaluates anything, so when the submit key arrives outside a reverse search, it leaves the buffer alone and returns Submit_Requested. The application reads Value and takes over.

The other actions are short. Ctrl-D on an empty buffer returns End_Of_Input, which ends the program. Ctrl-C returns Cancelled, which abandons the current input without submitting it.

Now Submit has a decision of its own, because not every submitted line is finished. Accept_Submission retains the text as the newest history entry, empties the buffer, and reports the submitted text. Insert_Continuation instead inserts one line feed at the cursor and keeps the input open.

Insert_Continuation performs a single undoable edit, and it reports Success => False when that line feed would exceed Max_Code_Points or Max_Lines. The buffer is then unchanged, which is why the branch above prints a problem line rather than assuming the line opened. Say appends one line to the session transcript, and its last argument is the line kind that Step 04 defines.

That leaves the question of which inputs are unfinished. The example treats an input as incomplete when a bracket is unclosed, or when the last non-blank character is an arithmetic operator.

In a real language, replace Needs_More with a call to the parser. A parser that reports an unexpected end of input answers the same question more accurately. Completeness depends on the language, so it stays application policy rather than a component setting.

Run the program now. Enter 1 + 2 and it answers = 3. Enter 1 + and it prints nothing: the prompt opens a second line and waits for the rest.

Step 03

Make room for the second line.

That second line is a problem. Step 01 created the prompt one row high, so the buffer now holds a line that the reader cannot see. The prompt has to grow with its content.

A continued input is buffer text containing line feeds. The prompt draws the primary marker on the first row of the first line; it draws the continuation marker on every later row, including a row produced by wrapping. It pads both markers to the same width, so buffer text starts in the same column on every row. Line_Editors calls that width the prompt gutter.

Derive the prompt height from the current line count, bounded by a maximum and by the rows the session has. The transcript takes whatever rows remain.

Editing itself delegates to Text_Areas. Grapheme clusters, whole-edit capacity refusal, and undo behave exactly as they do there.

A multi-line prompt also needs a key that opens a line without submitting, and no single key works on every terminal. A legacy terminal reports Shift-Enter as a bare carriage return, so it cannot tell Shift-Enter from Enter. It does encode Alt-Enter distinctly, and the editor accepts both encodings of Alt-Enter. Ctrl-O works on every terminal.

To do better, ask the terminal for the enhanced keyboard protocol. Set Enhanced_Keyboard on the View record that Flyology_TUI.Views declares. A terminal that implements the protocol then reports a modified Enter distinctly, so Shift-Enter opens a continuation line. A terminal without the protocol ignores the request.

The backend restores the previous keyboard mode when it closes, including after an exception. The same record also requests mouse motion reporting; Step 08 explains why the windowed placement needs it.

Enter :demo to load a three-line input. All three lines are visible, Up and Down move between them, and Ctrl-O opens a fourth. On a terminal with the protocol, so does Shift-Enter.

Checkpoint

Try the editing keys.

Before adding anything else, use what is already there. Apart from the case statement in Step 02, no key handling has been written, and yet the prompt answers the usual readline keys.

  • Movement. Ctrl-A moves to the start of the line and Ctrl-E to the end. Alt-B and Alt-F move the cursor one word.
  • Lines and history. Up and Down move between buffer lines. On the first line, Up recalls an older history entry; on the last line, Down recalls a newer one. Ctrl-P and Ctrl-N recall from any line.
  • Kill and yank. Ctrl-K, Ctrl-U, Ctrl-W, and Alt-D remove text into the kill buffer. Ctrl-Y inserts the kill buffer at the cursor.
  • Search and completion. Ctrl-R starts a reverse search, and Enter then accepts the match rather than submitting it. Tab requests completion, and Step 05 supplies the candidates it shows. Ctrl-T transposes the two grapheme clusters at the cursor.

The bindings are fixed, so an application uses them as they are. Each action is also a public operation, so an application that wants different keys can bind its own to the same behavior.

Ctrl-R is worth trying twice, once before Step 06 and once after. Until the history is stored, it can only search what you typed in the current run.

Step 04

Highlight the transcript.

The transcript works, but everything in it looks the same. An echoed expression, its result, and an error are indistinguishable at a glance.

Start by recording what each line is, and nothing about how it looks. The example names the transcript type Scrollback and its lines Log_Line.

Syntax color is different, because it varies within a line rather than across lines. Highlights carries it as a Span_Array: a sequence of styled half-open code-point ranges, which Highlights calls an overlay. Index order matters only where two spans overlap, and there the later span wins. A component reads the array during Render and does not retain it.

So scan each visible echoed line while drawing it.

Scanning at render time has two consequences. The cost tracks the number of visible lines, not the length of the transcript. Nothing caches an overlay either, so changing the language recolors the whole transcript on the next Render call.

The nested generic Lexers builds the overlay from the same token contract that Syntax_Editors uses, so one lexer serves both the prompt and the transcript.

Scanning a line each time it is drawn suits short lines. For a large editable document, use Syntax_Editors instead. It retains an incremental token cache and advances it under the budget passed to Advance_Highlighting.

Submit (1 + 2) * 3 and the echoed line now separates its numbers, operators, and brackets. Then enter :lang ada and submit an Ada declaration. The earlier lines are rescanned with the Ada lexer as soon as the next frame is drawn.

Step 05

Complete the word at the cursor.

Tab does nothing useful yet. It returns Completion_Requested, and Step 02 routed that to Offer_Completions, which has so far been empty.

A Completions model retains the candidates, the buffer range an accepted candidate replaces, and the current selection. It does not compute the candidates, because the candidate set depends on the language.

Ask the prompt for the word at the cursor, then offer candidates for exactly that range.

Apply_Completion later replaces that range in one undoable edit, so Ctrl-Z reverses an accepted candidate in a single step.

Which candidates to offer is a question about the word before the cursor, not only the word under it. After procedure, function, package, or type, the cursor sits where a new name is being declared. There is nothing sensible to suggest, so the example offers nothing and the popup closes.

Placement matters as much as content. Put the popup under the word rather than at the start of the line. Derive the rest of its geometry from the word and the session:

  • Size it to its widest candidate, bounded below by twelve cells and above by the session width.
  • Place it at the cursor column minus the width of the typed word.
  • Bound its height by eight lines and by a third of the terminal height.
  • Clamp the origin when the popup would otherwise extend past the session width.

Type :h and press Tab. The popup opens beneath the word and lists :help and :history. Type a longer expression, put the cursor back in the middle of it, and press Tab again: the popup follows the cursor.

Step 06

Keep the history between runs.

Up already recalls earlier lines, because Accept_Submission retains each one. All of them disappear when the process exits.

A Histories model holds entries in a ring buffer, bounded by an entry count and a total code-point budget. It renders nothing and performs no I/O; it walks entries newest first, runs the incremental reverse search, and returns the prefix suggestion a prompt draws after the cursor as ghost text.

Persistence is deliberately not part of it. The nested generic Stores transfers entries between the model and whatever an application stores them in. The instantiation supplies a store handle type and two operations; the generic supplies the oldest-first ordering and the capacity checks. Line_Editors nests the same generic as History_Stores, for the history a prompt owns.

Note where the two calls sit. Update must not perform blocking external I/O, so read the store before the runner starts and write it after the runner returns. An application that needs to save mid-session runs the store behind a command instead.

Three details matter when reading a store back:

  • Load appends rather than replaces, so a caller restoring into a history that already holds entries calls Forget_All first.
  • A store written by an earlier build may hold entries that exceed the current bounds. Load counts such an entry as refused instead of raising.
  • An entry may contain line feeds, so a line-oriented store encodes them before writing and decodes them on the way back.

Submit a few expressions, press Ctrl-D, and start the loop again. Press Up, and the entries from the previous run are there. Only the first session has a stored history; a session opened in Step 07 starts empty.

Step 07

Run several sessions.

One prompt is finished. Running several needs an array, a focus order, and a rule for which session draws on top. The example keeps the focused session last in the order, so a later window draws over an earlier one. A press inside a session focuses that session and raises it.

The two Live fields are not the same thing. The model-level Live counts the live sessions; the session-level Live marks one session as open.

With several sessions in hand, the question becomes where to put them. F2 cycles four placements:

  • Inline limits the transcript to its own line count, so the prompt sits below the last output.
  • Docked gives the transcript the remaining rows, so the prompt sits at the bottom of the terminal.
  • Windowed gives each live session a Windows frame.
  • Paneled tiles the live sessions with Panel_Groups.

The session record is identical in all four, which is what Step 01 left room for. Only sizing, routing, and the cursor offset adapt to the placement:

  • Size the session from Client_Region for a window, or from Pane_Region for a pane.
  • Route each mouse event to the host first. Localize an unclaimed event into the region before the prompt receives it.
  • Add the region origin to the row and column that Cursor_Row and Cursor_Column report.

Press F3 for a second session, then F2 to cycle the placements. The same record appears inline, docked, in its own window, and tiled in a panel.

Step 08

Let windows overlap and move.

The windowed placement has one visible fault. Open a second window over the first, and the second erases it.

Windows.Render returns a surface the size of the Workspace rectangle passed to it, and that surface is opaque everywhere outside the window bounds. Compositing it whole therefore erases a window already drawn. Crop it to the window bounds first.

Both steps use signed clipping, which keeps them valid when a window is partly offscreen.

One more detail decides whether a window can be dragged at all. Constrain_To cancels an active move or resize. Call it when the terminal resizes and when a session opens, but not on every event. Calling it on every event prevents any drag from completing.

Moving and resizing are drag gestures, and button events do not report the motion between a press and its release. This is why Step 03 set Result.Mouse to Cell_Motion.

Open two windows and drag one by its title bar across the other. It moves, it stays in front, and the window beneath it is still whole. Drag an edge or a corner to resize.
