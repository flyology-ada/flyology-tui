Guide

Build a read-eval-print loop.

Build a prompt that evaluates arithmetic across several lines, highlights the transcript it echoes, completes the word at the cursor, and keeps its history between runs. The last steps run several of these sessions at once, in windows or in panels.

Working baseline

Run the example.

The complete program is examples/src/repl.adb. Every extract below comes from it. The program uses the application loop from Application loop, so each extract belongs in Update or Present unless the text says otherwise.

The loop evaluates integer arithmetic. A word that starts with a colon, such as :demo, is a directive rather than an expression.

  • Enter 1 + 2 for a result.
  • Enter :demo to load a three-line input.
  • Enter :new to open a second session.
  • Press F2 to move the sessions between the four placements of Step 07.

The example renames the packages it uses. Editors is Line_Editors, Marks is Highlights, Frames is Windows, and Panels is Panel_Groups. Menus is its instantiation of the generic Completions, and Histories keeps its own name. Scrollback is the example's own transcript type, defined in Step 04.

Step 01

Define the session record.

Start with the state one loop owns: a prompt, a completion popup, a transcript, and a window frame. The record carries no host position, so Step 07 can place the same record in four different placements.

Line_Editors has no default for the prompt markers, the word separators, or the duplicate policy. Each value is application policy, so Create requires it.

The six capacities are discriminants, so the bounds are part of the model type. The two buffer bounds and the two history bounds behave differently when an operation exceeds them:

  • Max_Code_Points and Max_Lines bound the buffer. The model refuses the whole edit and leaves content, cursor, selection, and history unchanged.
  • Max_Undo_Entries, Max_Undo_Code_Points, Max_Recalled_Entries, and Max_Recalled_Code_Points bound the undo and command histories. The model evicts the oldest entry and applies the operation.

The separator set omits the colon, so a directive such as :help is one word. Step 05 depends on that.

Each session also needs its own screen position. Initialize replaces every frame with a staggered one, so a second window does not hide the first.

Step 02

Handle the submission action.

The record from Step 01 holds state but answers no keys. Feed each terminal event to the prompt, then act on the action it returns.

The editor does not evaluate whether an input is complete. When the submit key arrives outside a reverse search, the editor leaves the buffer unchanged and returns the action Submit_Requested. The application then reads Value.

Ctrl-D on an empty buffer returns End_Of_Input, which ends the program. Ctrl-C returns Cancelled, which abandons the current input.

Submit then chooses between two operations. Accept_Submission retains the text as the newest history entry, empties the buffer, and reports the submitted text. Insert_Continuation inserts one line feed at the cursor as a single undoable edit and keeps the input open. It reports Success => False when the line feed would exceed Max_Code_Points or Max_Lines, and then leaves the buffer unchanged.

The example treats an input as incomplete when a bracket is unclosed or the last non-blank character is an arithmetic operator. Entering 1 + therefore inserts a continuation line.

Replace Needs_More with a call to the language parser. A parser that reports an unexpected end of input decides the same question more accurately. Completeness depends on the language, so the completeness rule is application policy rather than a component setting.

Step 03

Size the prompt for multi-line input.

Insert_Continuation puts a second line in the buffer, so the prompt now needs more than the one row it was created with.

A continued input is buffer text containing line feeds. The prompt draws the primary marker on the first row of the first line. It draws the continuation marker on every later row, including a row produced by wrapping. It pads both markers to the same width, so the buffer text starts in the same column on every row. Line_Editors calls that width the prompt gutter.

Derive the prompt height from the current line count. The transcript then takes the rows that remain.

Editing delegates to Text_Areas. Grapheme clusters, whole-edit capacity refusal, and undo behave as they do in Text_Areas.

Step 04

Highlight the transcript lines.

Accept_Submission reports the submitted text. Append that text to the session's Log field, together with the result of evaluating it.

Each transcript line stores its text and a kind, but no style. The example names the transcript type Scrollback and its lines Log_Line.

Highlights declares the type that carries the coloring. A Span_Array is a sequence of styled half-open code-point ranges, and Highlights calls one such array an overlay. Index order matters only where two spans overlap, where the later span wins. A component reads the array during Render and does not retain it.

Scan each visible echoed line while drawing it. The scan covers only the lines the viewport shows, so its cost follows the number of visible lines rather than the transcript length. Because no overlay is cached, a language change recolors the whole transcript on the next Render call.

The nested generic Lexers builds the overlay from the token contract that Syntax_Editors uses, so one lexer serves the prompt and the transcript.

Scanning each line as it is drawn suits short lines. For a large editable document, use Syntax_Editors. It retains an incremental token cache and advances it under the budget passed to Advance_Highlighting.

Step 05

Compute and offer completion candidates.

The prompt now accepts and echoes input. Tab still returns Completion_Requested with nothing to show, because Step 02 left Offer_Completions empty.

A Completions model retains the candidates, the buffer range an accepted candidate replaces, and the selection. The application computes the candidates, because the candidate set depends on the language.

Request the word at the cursor, then offer candidates for that range. Apply_Completion performs one undoable edit.

The example matches candidates against the word at the cursor. The word before it decides whether any are offered at all. After procedure, function, package, or type, the cursor is at a declared name. The example then offers nothing, and the popup closes.

Place the popup under the word rather than at the start of the line. Size it to its widest candidate, bounded below by twelve cells and above by the session width. Then place it at the cursor column minus the width of the typed word. Bound its height by eight lines and by a third of the terminal height. When the popup would extend past the session width, clamp the origin.

Step 06

Persist the history through a store.

Accept_Submission already retains each entry, but only until the process exits. Persist those entries through a store.

A Histories model retains entries in a ring buffer bounded by an entry count and a total code-point budget. It performs no rendering and no I/O. It walks entries newest first, runs the incremental reverse search, and returns the prefix suggestion that a prompt draws after the cursor as ghost text.

The nested generic Stores transfers entries between the model and an application store. The instantiation provides a store handle type and two operations; the generic provides the oldest-first ordering and the capacity checks. Line_Editors nests the same generic under the name History_Stores, for the history that a prompt owns.

Update must not perform blocking external I/O. Read the store before the runner starts and write it after the runner returns, or run the store behind a command.

Load appends rather than replaces, so a caller restoring into a history that already holds entries calls Forget_All first.

A store written by an earlier build may contain entries that exceed the current bounds. Load counts such an entry instead of raising.

An entry may contain line feeds, so a line-oriented store encodes them before writing.

The example keeps one stored history, and it belongs to the first session. A session opened in Step 07 starts with an empty history.

Step 07

Host several sessions.

One session is complete. Running several needs an array and a focus order. The example keeps the focused session last in the order, so a later window draws over an earlier one. A press inside a session focuses that session and raises it.

The model-level Live counts the live sessions, and the session-level Live marks one session as open.

F2 cycles four placements:

  • Inline limits the transcript to its own line count, so the prompt sits below the last output.
  • Docked gives the transcript the remaining rows, so the prompt sits at the bottom of the terminal.
  • Windowed gives each live session a Windows frame.
  • Paneled tiles the live sessions with Panel_Groups.

The session record is identical in all four. Adapt sizing, routing, and cursor offset to the placement:

  • Size the session from Client_Region for a window, or from Pane_Region for a pane.
  • Route each mouse event to the host first. Localize an unclaimed event into the region before the prompt receives it.
  • Add the region origin to the row and column that Cursor_Row and Cursor_Column report.
Step 08

Compose overlapping windows.

Two details belong to the windowed placement alone.

The first is drawing. Windows.Render returns a surface the size of the Workspace rectangle passed to it. That surface is opaque everywhere outside the window bounds, so compositing it whole would erase a window already drawn. Crop it to the window bounds first.

Signed clipping keeps both steps valid when a window is partly offscreen.

The second is gesture lifetime. Constrain_To cancels an active move or resize. Call it when the terminal resizes and when a session opens, but not on every event. Calling it on every event prevents any drag from completing.

Step 09

Use the readline bindings.

The prompt now works in four placements. Its key bindings are fixed, so an application uses them rather than setting them.

  • Movement. Ctrl-A moves to the start of the line and Ctrl-E to the end. Alt-B and Alt-F move the cursor one word.
  • Lines and history. Up and Down move between buffer lines. On the first line, Up recalls an older history entry; on the last line, Down recalls a newer one. Ctrl-P and Ctrl-N recall from any line.
  • Kill and yank. Ctrl-K, Ctrl-U, Ctrl-W, and Alt-D remove text into the kill buffer. Ctrl-Y inserts the kill buffer at the cursor.
  • Search and completion. Ctrl-R starts a reverse search, and Enter then accepts the match rather than submitting it. Tab requests completion. Ctrl-T transposes the two grapheme clusters at the cursor.

Each action is also a public operation, so an application can bind its own keys to them.

Step 10

Request the terminal modes.

Two behaviours need the terminal's cooperation, so Present requests them on the view it returns.

The first is the continuation key. A legacy terminal reports Shift-Enter as a bare carriage return, so it cannot distinguish Shift-Enter from Enter. It encodes Alt-Enter distinctly, and the editor accepts both encodings of Alt-Enter. Ctrl-O inserts a continuation line on every terminal.

Set Enhanced_Keyboard on the View record that Flyology_TUI.Views declares to request the enhanced keyboard protocol. A terminal that implements the protocol reports a modified Enter distinctly, so Shift-Enter inserts a continuation line. A terminal without the protocol ignores the request. The backend restores the previous keyboard mode when the backend closes, including after an exception.

The second is the mouse. Moving and resizing a window are drag gestures. Button events do not report the motion between a press and its release, so request motion reporting.
